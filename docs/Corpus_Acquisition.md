Corpus Acquisition

Corpus acquisition: specification for the Phase 0 / foundation corpus tasks (CUAD + EDGAR). Fold this into the relevant foundation tasks (corpus acquisition, ontology/registry derivation, eval-set construction) and their acceptance criteria.
License and provenance to record. CUAD v1 is CC BY 4.0 (verify at download and record the attribution). EDGAR data is public, no API key. Note in the corpus ADR that CUAD is single-domain legal, so the generic-RAG generality claim needs a second domain later.
Two acquisition scripts (ordinary foundation work, gitignore the outputs per the data-artifacts rule).
CUAD subset fetch. Source: HuggingFace theatticusproject/cuad-qa for the SQuAD-style span answers; the GitHub repo or Zenodo for the contract PDFs and the master-clauses CSV. Pull three artifacts: a subset of contract PDFs (for the Docling parse and vision-to-text path), the master-clauses CSV (the 41-category expert annotations, the extraction and clause-finding ground truth), and the SQuAD JSON (span answers). Target ~100MB, roughly 100 to 150 contracts. Subset-selection criteria (this is the judgment part, do not select randomly): include some scanned PDFs so the vision-to-text ingestion path is exercised; spread across the 25 agreement types rather than clustering one; and deliberately include multi-party contracts and contracts sharing parties, since those are what make the relational and multi-hop eval questions possible. Record the selection criteria and the resulting manifest so the subset is reproducible.
EDGAR entity fetch. Download https://www.sec.gov/files/company_tickers.json once as the registry seed (CIK, ticker, conformed name for all public companies). For the subset's parties, fetch https://data.sec.gov/submissions/CIK##########.json for former-names and ticker aliases (needed for entity-resolution alias handling). Two mandatory operational constraints: send a User-Agent header identifying the caller (EDGAR rejects requests without one), and throttle to at most 10 requests per second with a delay between calls and local caching of responses. CIK is 10-digit zero-padded, which is the canonical EntityId form from T1, so the T8 registry loader's normalization is exactly zero-pad-to-10-then-validate against the strict EntityId contract.
The name-to-CIK link and the eval-key discipline (important, do not auto-generate the key). CUAD does not ship a CIK per contract, so linking a contract's parties to EDGAR CIKs is a company-name-to-registry match. That match is itself the entity-resolution problem (FR-C.7), so using fuzzy matching to build the eval answer key and then testing fuzzy matching against that key is circular. Therefore: the script may propose name-to-CIK matches mechanically, but the entity-resolution eval subset and the relational/multi-hop eval questions must be human-verified before they become ground truth. Build the eval set so the proposed matches are presented for human review and only the verified ones enter the golden set. This is the same human-curated-fixture discipline used for the engine's control_level eval.
Where each output lands. The company_tickers.json plus submissions data feeds the registry-derivation foundation task (builds the entity registry, FR-C.8). The CUAD master-clauses annotations feed the extraction and clause-finding eval questions directly. The EDGAR entity links feed the relational and multi-hop eval questions (human-verified). The ontology-derivation task uses the 41 CUAD clause categories plus party and entity types.
Network note. If Claude Code's sandbox does not have huggingface.co, sec.gov, data.sec.gov, and zenodo.org allowlisted, either those domains get added for the acquisition step, or the human fetches the files once and places them in the repo's (gitignored) data directory for Claude Code to work from. The download is one-time and the files then live locally, so either path is fine; flag which one before running the scripts.
Acceptance criteria to attach. The corpus subset is reproducible from a recorded manifest and selection criteria; the EDGAR fetch uses a User-Agent and respects the 10-req/s limit; the entity registry loads and normalizes real messy EDGAR CIK forms to canonical EntityId (ties to the T8 test); and the golden eval set has questions in all four archetypes, with the relational and multi-hop questions human-verified, not auto-generated.
